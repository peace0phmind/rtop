# Ontop→rtop 迁移决策循环

## 目的

持续清除 Rust 迁移路线图中的一个最前置决策票据，把参考 Ontop 的可观察语义转为
可实现、可验证且不带 Java 宿主依赖的约束。

## Trigger

路线图中存在一个所有阻塞项均已关闭的迁移决策 issue，或该 issue 的最新证据使其
可以继续。

## 每次运行

1. 选择最前置的开放 issue，读取其问题、路线图约束和已关闭决策。
2. 从固定 Ontop 提交的源码、POM、测试、配置与 Docker 场景收集能回答该 issue 的
   事实；运行所需的 Docker/JDK 11 或 17 参考验证。不得询问用户可由这些材料确认
   的问题。
3. 将发现写入 `docs/research/`，明确区分：保留的跨语言语义、Rust 自有实现、可选
   adapter 与 Java/JDBC 宿主排除项。
4. 用可复现命令、测试结果和源码位置检查文档；将简短结论与证据写入 issue。
5. 关闭已解决的 issue，并在路线图 issue #1 勾选该项、添加一条决策摘要。随后回到
   Trigger。

## Checkpoint

默认无 checkpoint。仅当以下任一条件出现时，在完成全部可做取证后给出 brief：

- 所需功能会突破“无 JVM/JDBC/Java 进程内 API”的范围；
- 需要用户提供凭证、购买/再分发许可或联系外部厂商；
- 现有源码、测试和文档不足以在不猜测的情况下选择兼容行为；
- 两种实现路线都会明显改变产品范围、兼容性或成本。

## Brief

只包含：阻塞的具体决定、已验证事实、推荐选择、影响范围，以及相关 issue/文档的
链接。不得要求用户阅读原始日志或草稿。

## 完成条件

该 issue 已有可追溯的证据和决策记录、路线图已更新，且下一个无阻塞 issue 已被
选择或已进入其事实收集阶段。
